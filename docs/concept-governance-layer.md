# 개념: 거버넌스(Governance)와 이 프로젝트의 위치

[comparison-native-multi-agent.md](comparison-native-multi-agent.md) 결론에서 이 프로젝트를 "네이티브 전송 계층 위/별개의 거버넌스 계층"이라고 정리했는데, "거버넌스"라는 용어 자체가 모호할 수 있어 별도로 풀어 정리한다. §3의 "SendMessage와 거버넌스를 조화시킨다면"은 처음엔 검증되지 않은 아이디어였으나, §4에서 격리된 세션으로 1차 실측을 마쳤다(2026-09-07). 다만 실제 프로덕션 프로젝트 연동까지 끝난 건 아니라 여전히 최종 결론은 아니다.

## 용어: "멀티 에이전트"와 "멀티 에이전트 파이프라인"은 다른 개념이다

이 문서 전체에서 쓰는 "거버넌스 계층"이라는 말과 같은 얘기지만, 두 용어 자체를 먼저 구분해두면 이해가 쉽다.

- **멀티 에이전트**는 여러 에이전트가 존재하고 서로 메시지를 주고받을 수 있다는 **능력(capability)**을 가리킨다. 네이티브 `Agent`+`SendMessage`가 정확히 여기에 해당한다.
- **멀티 에이전트 파이프라인**은 그 능력 위에 시작 → 검증 → 승인 → 종료라는 **정해진 처리 흐름(process)**을 얹은 것을 가리킨다. 이 프로젝트(`ai-development-orchestrator`)가 정확히 여기에 해당한다 — 능력을 원재료로 삼아 승인 게이트·신원 검증·기록까지 정의해둔 것이다.

두 개념은 서로 무관한 게 아니라, 파이프라인이 멀티 에이전트 능력을 전제로 하는 **상위 개념**이라는 관계다 — 파이프라인이 성립하려면 그 밑에 어떤 형태로든 "에이전트끼리 실제로 메시지를 주고받는 수단"이 있어야 한다. 아래 §1~2에서 다루는 "거버넌스"는, 이 상위 개념(파이프라인)이 능력 위에 구체적으로 무엇을 얹는지를 풀어낸 것이다.

## 1. 거버넌스란

일반적인 의미에서 거버넌스는 "누가, 언제, 어떤 절차를 거쳐, 어떤 근거로 결정을 내리는가"를 관리하는 체계다. 통신·행동 자체가 아니라 **그 통신·행동에 대한 통제 규칙과, 그 규칙이 지켜지는지 확인하는 절차**를 가리킨다. 소프트웨어에서 자주 쓰는 하위 개념:

| 개념 | 질문 |
|---|---|
| 승인(approval) | 이 행동을 실행하기 전에 누가 허락해야 하는가? |
| 신원 검증(identity/authN) | 이걸 요청한 게 정말 그 주체가 맞는가? |
| 권한 제한(authZ, 최소 권한) | 이 역할은 애초에 무엇까지 할 수 있는가? |
| 감사(audit) | 언제 무슨 일이 있었는지 나중에 확인할 수 있는가? |
| 의사결정 기록(decision record) | 왜 그렇게 결정했는지 근거가 남아있는가? |

이 프로젝트가 위 다섯 요소를 각각 어떻게 구현하는지는 이미 [comparison-native-multi-agent.md §2](comparison-native-multi-agent.md#2-항목별-비교)에 정리되어 있다.

| 거버넌스 요소 | 이 프로젝트에서의 구현 |
|---|---|
| 승인 | `ask_agent`/`answer_question`이 `admin-cli`로 Human이 승인할 때까지 보류됨 |
| 신원 검증 | `ORCHESTRATOR_AGENT_ID`로 `from_agent_id` 거짓 주장 탐지·거부 |
| 최소 권한 | Scribe Agent는 `submit_decision_record` 도구 하나만 가짐 |
| 감사 | Event Log에 모든 Hook/Q&A 이벤트가 시간순으로 기록 |
| 의사결정 기록 | 거절 사유가 있으면 Decision Record 초안이 자동 생성되고 사람이 승인 |

## 2. 왜 네이티브 `SendMessage`는 "거버넌스가 없다"고 하는가

`SendMessage({ to, message })`는 이름만 알면 누구든 호출할 수 있고, 승인·신원 검증·감사 로그 없이 바로 상대 세션에 전달된다. 이건 결함이 아니라 **애초에 그런 걸 하려고 만든 도구가 아니기 때문**이다 — 메시지를 "전달"하는 데만 집중한 순수 전송 프리미티브다. [requirements.md §7](requirements.md#7-agent-간-통신) "Agent 간 직접 통신 금지" 원칙, [architecture.md §3](architecture.md#3-agent-간-통신-강제-7-대응)의 물리적 단일 통로 강제는 이 전제를 의도적으로 뒤집은 것이다.

## 3. SendMessage와 거버넌스를 조화시킨다면

떠오른 방향은 **`SendMessage`를 전송 수단으로 그대로 쓰되, `PreToolUse` Hook으로 그 호출을 가로채서 지금의 승인/신원검증/기록 파이프라인에 태우는 것**이다. 지금의 커스텀 `ask_agent` MCP 도구 대신 네이티브 `SendMessage`를 허용하고, 호출 직전에 Hook이 가로채 Question Eligibility Check → Human 승인 대기 → 승인되면 통과, 거절되면 차단하는 흐름을 상상해볼 수 있다. 이러면 전송 계층(MCP 서버)을 직접 구현·유지보수할 필요가 줄어든다.

다만 트레이드오프가 있다. 지금 구조의 핵심 강점은 "Agent에게 통신 도구가 물리적으로 `ask_agent` 하나뿐이라 우회가 원천 불가능하다"는 **구조적 보장**([architecture.md §3](architecture.md#3-agent-간-통신-강제-7-대응))이다. `SendMessage`를 허용하고 Hook으로 가로채는 방식은 이 보장이 "Hook이 `SendMessage` 호출을 정말 예외 없이 가로챌 수 있는가"라는 전제에 의존하게 된다. §4.1에서 이 전제의 핵심 부분(관찰·차단·장시간 보류)은 실측으로 확인됐지만, "예외 없이"(서브에이전트 경유 우회 가능성 등)까지는 아직 완전히 닫히지 않았다 — §4.2 참고.

## 4. 검토 결과

### 4.1 1차 실측 (2026-09-07, 격리된 세션)

이 저장소도, 사용자의 실제 FE/API 프로덕션 프로젝트도 아닌 별도의 격리된 임시 디렉터리에서, 순수 헤드리스 `claude -p` 세션으로 아래를 실측했다. `investigation-mcp-session-delay.md`와 같은 원칙(실제 세션 소모 최소화, 저비용 확인부터)을 따랐다.

| 항목 | 결과 |
|---|---|
| `PreToolUse` Hook이 `SendMessage`를 관찰할 수 있는가 | **가능**. matcher `"SendMessage"`로 정확히 잡혔고, `tool_input`에 `to`/`message`/`summary`/`type`/`recipient`/`content` 등 전체 페이로드가 노출됨 |
| Hook이 실제로 차단할 수 있는가 | **가능**. `permissionDecision: "deny"` 응답 시 도구 호출이 막히고, 모델이 그 사유를 그대로("훅에 의해 차단되었습니다") 정직하게 사용자에게 보고함 — 할루시네이션 없이 |
| 오래 붙잡고 있어도 안전한가 (Human 승인 대기 시뮬레이션) | **최소 70초까지 안전 확인**. Hook 스크립트가 70초 `sleep` 후 `allow`를 반환했는데, Hook 자체의 숨겨진 타임아웃 없이 정확히 70초 뒤 재개됨 — `AskUserQuestion`의 60초 AFK 타임아웃([investigation-native-askuserquestion-timeout.md](investigation-native-askuserquestion-timeout.md))과 달리 이 경로는 그 시점을 넘겨도 살아있었음 |

**부수 발견**: 70초 대기 뒤 `allow`로 통과시켰는데도, 존재하지 않는 이름(`hook-test-target-2`)으로는 SendMessage 자체가 "에이전트를 찾을 수 없다"며 실패했다. 즉 대상 이름이 미리 존재해야 하는 것으로 보이며, [comparison-native-multi-agent.md §1](comparison-native-multi-agent.md#1-두-메커니즘-개요)에서 언급했던 "처음 보는 이름이면 새 세션이 시작된다"는 설명은 적어도 이 경로에서는 재현되지 않았다(반증까지는 아니고, 별도 확인 필요한 불일치로 남겨둔다).

### 4.2 아직 확인되지 않은 것

- **우회 불가능성**: 서브에이전트(Task) 경유로 `SendMessage`를 호출해도 같은 Hook이 발동하는지는 직접 재현하지 않았다. 공식 문서는 "Hook은 서브에이전트 내부에서도 동일하게 발동한다"고 명시하지만, 이 저장소의 다른 문서들과 같은 기준으로 보면 지금은 "문서 근거"이지 "실측 확인"은 아니다.
- **완전 대체 vs 병행**: 커스텀 MCP 서버(`ask_agent`/`answer_question`)를 이 방식으로 완전히 대체할지 병행할지는 설계 판단이라 이번 실측 대상이 아니었다.
- **실제 프로덕션 프로젝트 연동**: 위 실측은 전부 격리된 임시 디렉터리에서 이뤄졌다. 실제 FE/API 프로젝트의 Agent 로스터·Human 승인 흐름에 그대로 옮겨서도 같은 결과가 나오는지는 별도 확인이 필요하다.

## 5. 결론 (갱신)

§3의 조화 방안은 더 이상 순수 아이디어 단계가 아니다 — 핵심 메커니즘(관찰·차단·장시간 보류)이 격리된 환경에서 실측으로 확인됐다. 다만 "우회 불가능성"과 "실제 프로덕션 연동"이라는 두 조건이 남아있는 한, 현재 구현(물리적 단일 통로)을 완전히 대체할 근거로 쓰기엔 아직 이르다.
